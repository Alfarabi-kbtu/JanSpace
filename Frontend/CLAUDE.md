# JanSpace — Frontend (Next.js)

Этот файл читается Claude Code в начале каждой сессии в этом проекте.
Фронтенд — отдельный проект рядом с бэкендом (`C:\JanSpace\Backend\`,
свой CLAUDE.md там). Держи этот файл актуальным так же, как бэкендовский:
если Claude делает ошибку из-за незнания API бэкенда — допиши её сюда.

Строка `@AGENTS.md` выше — импорт файла, который перегенерирует сам
`next dev` при каждом запуске (версии Next.js/breaking changes). Не
удаляй её и не переноси контент AGENTS.md сюда вручную — он и так
подключается автоматически.

## Что это за проект

Next.js-фронтенд для JanSpace. Бэкенд — Django REST Framework
(`C:\JanSpace\Backend\`), полностью отдельный процесс/деплой (прод —
Railway). Ниже описан именно контракт бэкенда: какие эндпоинты есть,
что они принимают/отдают и какие особенности нужно учитывать —
чтобы фронтенд не пришлось переделывать под реальное API постфактум.

## Стек

TypeScript, App Router, Tailwind CSS, npm — выбрано при создании
проекта через `create-next-app`.

## Переменные окружения фронтенда

- `NEXT_PUBLIC_API_URL` — базовый URL бэкенда (`http://localhost:8000`
  локально при поднятом `docker compose` в Backend, Railway-домен в проде).
  Префикс `NEXT_PUBLIC_` обязателен — иначе переменная не попадёт в
  клиентский JS-бандл Next.js.
- `NEXT_PUBLIC_WS_URL` — базовый WebSocket URL (`ws://localhost:8000`
  локально, `wss://<railway-домен>` в проде — обязательно `wss://`,
  не `ws://`, если сайт открыт по https, иначе браузер заблокирует
  mixed-content соединение).

## Локальная разработка

Перед запуском фронтенда бэкенд должен быть поднят
(`docker compose up -d` в `C:\JanSpace\Backend\`) — иначе все запросы
будут падать с connection refused. Порт фронтенд-дев-сервера должен
совпадать с тем, что разрешён в `CORS_ALLOWED_ORIGINS` бэкенда
(по умолчанию там `http://localhost:3000` и `http://127.0.0.1:3000` —
это стандартный порт Next.js dev-сервера, менять не придётся, если не
переопределяли `-p` при `next dev`).

### Через Docker

У фронтенда есть свой `Dockerfile` (dev-режим: `next dev` + смонтированный
код, аналогично `runserver` у бэкенда), но собственного
`docker-compose.yml` у фронтенда нет — сервис `frontend` добавлен прямо в
`C:\JanSpace\Backend\docker-compose.yml` (build-контекст `../Frontend`),
чтобы весь стек поднимался одной командой:

```
cd C:\JanSpace\Backend
docker compose up -d --build
```

Это поднимет `db`, `redis`, `web` (:8000) и `frontend` (:3000) вместе.
Особенности:

- `node_modules` и `.next` — **отдельные именованные Docker-volume**, не
  часть смонтированного кода. Если бы они монтировались с хоста как есть,
  внутрь Linux-контейнера попал бы Windows-собранный `node_modules`
  (нативный бинарник Turbopack под Windows несовместим с Linux). Именованный
  volume при первом запуске сам наполняется содержимым из образа (где
  зависимости уже поставлены через `npm ci` под Linux).
- `NEXT_PUBLIC_API_URL`/`NEXT_PUBLIC_WS_URL` в контейнере фронтенда
  остаются `http://localhost:8000`/`ws://localhost:8000`, а не
  `http://web:8000` — эти переменные уходят в браузер и читаются оттуда,
  а браузер обращается к опубликованным портам на хосте, а не к
  внутренней docker-сети. Менять их на имя сервиса — ошибка.
- После `npm install` нового пакета на хосте образ фронтенда нужно
  пересобрать (`docker compose up -d --build frontend`) — именованный
  volume с `node_modules` сам не подхватит новые записи в
  `package.json`/`package-lock.json`, если их не переустановить.

## Аутентификация (JWT)

- `POST /api/token/` `{username, password}` → `{access, refresh}`.
  Троттлинг 5 попыток/минуту с одного IP (429 после превышения — это
  ожидаемое поведение бэкенда, не баг, см. ниже).
- `POST /api/token/refresh/` `{refresh}` → `{access}`.
- `POST /api/register/` `{username, email, password, password2}` →
  201 `{user: {id, username, email}, refresh, access}`. Токены отдаются
  сразу — отдельный вызов `/api/token/` после регистрации не нужен.
- Access-токен живёт 60 минут, refresh — 7 дней (`SIMPLE_JWT` в
  бэкендовском `settings.py`).
- Каждый запрос к защищённым эндпоинтам — заголовок
  `Authorization: Bearer <access>`.
- Refresh-flow реализован в `src/lib/api.ts` (`authRequest` +
  `refreshAccessToken`, используются через `apiGet`/`apiPatch`/
  `apiAuthPost`): при 401 один раз пробует `/api/token/refresh/` и
  повторяет исходный запрос; параллельные 401 дедуплицируются в один
  refresh через модульный `refreshPromise`. Если refresh тоже упал —
  токены чистятся (`clearTokens()`), и запрос падает с исходной 401;
  вызывающий код (см. `src/app/profile/page.tsx`) сам решает
  редиректить на `/login`. `apiPost` (без auth) для публичных
  эндпоинтов (`/api/token/`, `/api/register/`, `/api/password-reset/*`)
  этот флоу не трогает — там 401 означает просто неверный пароль,
  а не истёкший токен.

### Сброс пароля

- `POST /api/password-reset/` `{email}` → всегда 200, независимо от того,
  существует ли такой email (защита от перебора почт) — не полагайтесь
  на этот ответ, чтобы понять, найден ли пользователь.
- Если email найден, письмо со ссылкой уходит на
  `FRONTEND_RESET_PASSWORD_URL` (задаётся в `.env` бэкенда, например
  `https://<фронтенд-домен>/reset-password`) с параметрами
  `?uid=...&token=...`. **Фронтенд обязан иметь роут по ЭТОМУ ЖЕ пути**
  (по умолчанию `/reset-password`), который читает `uid`/`token` из
  query-строки и отправляет их дальше.
- `POST /api/password-reset/confirm/`
  `{uidb64, token, password, password2}` → 200 при успехе, 400 с ошибкой
  в `token`/`uidb64`, если ссылка невалидна или уже использована.

### Профиль

- `GET/PUT/PATCH /api/profile/` (нужен `Authorization`) →
  `{id, username, email, first_name, last_name}`. `username` — read-only,
  сменить логин через этот эндпоинт нельзя.
- `POST /api/change-password/` (нужен `Authorization`)
  `{old_password, new_password, new_password2}`.

## REST-ресурсы

Все — стандартные DRF `ModelViewSet` через `DefaultRouter`
(`GET`/`POST` на `/api/<ресурс>/`, `GET`/`PUT`/`PATCH`/`DELETE` на
`/api/<ресурс>/<id>/`).

| Эндпоинт | Права | Заметки |
|---|---|---|
| `/api/categories/` | чтение — всем, запись — только `is_staff` | см. "Известные особенности" ниже про `product_category`/`service_category` |
| `/api/products/` | чтение — всем, запись — только `is_staff` | фильтры `?is_available=&product_category=<id>` |
| `/api/services/` | чтение — всем, запись — только `is_staff` | фильтры `?is_available=&service_category=<id>` |
| `/api/orders/` | только авторизованные, каждый видит только свои | `order_id` — **UUID**, не число |
| `/api/complaints/` | только авторизованные, каждый видит только свои | `user` проставляется сервером сам, в теле запроса его не передавать |
| `/api/messengers/` | чтение — всем, запись — только `is_staff` | по сути один "singleton"-объект со ссылками на соцсети — GET список и берите первый элемент |

### Пагинация

Все list-эндпоинты возвращают не голый массив, а:
```json
{ "count": 42, "next": "http://.../?page=2", "previous": null, "results": [...] }
```
`PAGE_SIZE=20`. Всегда разворачивайте `.results`.

### Заказы (`/api/orders/`)

- `product`/`services` в ответе — вложенные полные объекты (для чтения).
- При создании/обновлении используйте `product_ids`/`service_ids` —
  массивы ID товаров/услуг (не полные объекты).
- Заказ обязан содержать хотя бы один товар ИЛИ одну услугу — иначе 400
  с `non_field_errors`.
- `order_status`: `pending` / `processing` / `completed` / `cancelled`.
  Клиент обычно не меняет статус сам (это делает админ/бэкофис) — но
  через `PATCH` технически можно, если понадобится.
- `order_id` — **UUID-строка**, не целое число. При построении путей
  (`/api/orders/<id>/`) и роутов фронтенда учитывайте это в типах.

### Изображения (`/api/products/`, `/api/services/`)

- Поле `image` — загрузка через `multipart/form-data`, не JSON.
- В ответе `image` — уже полный абсолютный URL на S3
  (`https://<bucket>.s3.<region>.amazonaws.com/...`) — НЕ конкатенируйте
  его с `NEXT_PUBLIC_API_URL`, используйте как есть.
- Известная особенность бэкенда: если поле `is_available` не передано
  явно при отправке `FormData` (например, при загрузке картинки), DRF
  считает его `false` — в отличие от JSON-запросов, где отсутствующее
  поле просто не тронет текущее значение при `PATCH`. При отправке
  `FormData` всегда явно добавляйте `is_available` (`"true"`/`"false"`
  строкой), если хотите его сохранить.

## WebSocket — статус заказа в реальном времени

- URL: `${NEXT_PUBLIC_WS_URL}/ws/orders/?token=<access-токен>` — JWT
  передаётся через query-параметр `token`, не через заголовок (браузер
  не может добавлять кастомные заголовки к WebSocket-хендшейку).
- Если токен невалиден/просрочен — сервер сразу закрывает соединение.
  Значит: при обновлении access-токена через refresh-flow нужно
  переоткрыть WebSocket с новым токеном в query-строке — на лету токен
  внутри уже открытого соединения не подменить.
- Соединение однонаправленное: сервер сам присылает события, клиент
  ничего в этот сокет не отправляет — только слушает.
- Формат входящего сообщения:
  ```json
  { "order_id": "uuid-строка", "order_status": "processing" }
  ```
- Каждый пользователь получает события только по СВОИМ заказам —
  фильтрация уже сделана на сервере, на фронте ничего фильтровать не нужно.

Реализовано в `src/lib/order-status.ts` (`useOrderStatusUpdates`) —
используется в `src/app/orders/page.tsx` и `src/app/orders/[id]/page.tsx`,
обновляет `order_status` в стейте по приходящим событиям. При закрытии
сокета (просроченный токен, разрыв сети) переподключается через 3с с
актуальным на тот момент access-токеном — так неявно подхватывается и
токен, обновлённый через refresh-flow за это время. Без токена (разлогинен)
соединение не открывается вовсе.

## Тесты

`npm test` — юнит-тесты через Vitest (`vitest run`; `npm run test:watch`
для watch-режима), конфиг в `vitest.config.mts` (jsdom + `vite-tsconfig-paths`
для алиаса `@/*`, как в `tsconfig.json`). Покрыты только `src/lib/*` — вся
"бизнес-логика" фронтенда, не завязанная на конкретную страницу:

- `api.test.ts` — самое важное здесь: refresh-flow (`authRequest`/
  `refreshAccessToken`) с мокнутым `fetch` — 401 → один retry, дедуп
  параллельных 401 в один `/api/token/refresh/`, откат к исходной 401 и
  `clearTokens()` если refresh тоже упал, `apiPost`/`apiPublicGet` не
  цепляют Authorization.
- `auth.test.ts`, `cart.test.ts` — хранение в localStorage +
  `AUTH_CHANGE_EVENT`/`CART_CHANGE_EVENT` (в т.ч. `useCart` через
  `renderHook` из `@testing-library/react`).
- `errors.test.ts`, `format.test.ts` — `parseApiError` на реальных формах
  ответов DRF (429, `detail`, `non_field_errors`, ошибки по полям) и
  форматирование цены/даты/статуса заказа.

Страницы (`src/app/**`) юнит-тестами не покрыты — вместо этого при каждой
фиче они прогонялись вручную через реальный контейнеризованный бэкенд
(`docker compose up -d` в Backend, см. раздел про Docker выше). E2E-тесты
(Playwright/Cypress) на страницы — следующий логичный шаг, если понадобится
покрытие выше уровня `lib/`.

## Известные особенности бэкенда (НЕ баги)

Эти вещи могут выглядеть как ошибка на фронте, но так и задумано:

1. **`Category` имеет `product_category` и `service_category` —
   отдельные строковые поля, а не одно общее `name`.** Одна и та же
   категория может использоваться и для товаров, и для услуг.
2. **`order_id` — UUID, не число.**
3. **Регистрация сразу возвращает `access`/`refresh`** — отдельный логин
   после регистрации не нужен и будет лишним запросом.
4. **`429 Too Many Requests`** после нескольких попыток логина/регистрации/
   сброса пароля — это троттлинг бэкенда (5/мин, 5/мин, 3/мин
   соответственно), не баг. Показывайте пользователю "слишком много
   попыток, попробуйте позже", не делайте retry-петлю.
5. **`is_available=false` при отправке `FormData` без явного значения
   поля** — см. раздел про изображения выше.
6. **Ответ `/api/password-reset/` одинаковый и для существующего, и для
   несуществующего email** — так и задумано, это защита от перебора почт.
